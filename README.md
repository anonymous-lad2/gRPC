## What this project is

We are building a minimal **gRPC UserService** in Python:

- **Phase 1 (done):** End-to-end **Unary RPC** — client sends one request, server returns one response.
- **Phase 2 (done):** Wire-format deep dive (serialization, framing, metadata, errors, deadlines).
- **Phase 3 (in progress):** Streaming RPCs (server streaming, client streaming, bidirectional).

The service exposes one RPC:

```
GetUser(UserRequest) → User
```

Example: client asks for user `id=1`, server returns name and email.

## Start from scratch (full setup)

Run these commands from an empty folder (or clone/reset this repo):

```bash
# 1. Create and activate a virtual environment (recommended)
python -m venv .venv
source .venv/bin/activate   # Linux/macOS
# .venv\Scripts\activate    # Windows

# 2. Install dependencies
pip install -r requirement.txt

# 3. Verify protoc is available via grpcio-tools
python -m grpc_tools.protoc --version

# 4. Create proto and generated folders (if not present)
mkdir -p protos generated
touch generated/__init__.py

# 5. Write protos/user.proto (see [Proto definition](#protosuserproto) below)

# 6. Compile the proto
python -m grpc_tools.protoc \
  -I protos \
  --python_out=generated \
  --grpc_python_out=generated \
  protos/user.proto

# 7. Fix generated imports (see [Import fix after code generation](#import-fix-after-code-generation))

# 8. Create server.py and client.py (see walkthrough below)

# 9. Run (two terminals)
python server.py    # Terminal 1
python client.py    # Terminal 2
```

Expected client output:

```
id: 1
name: "John Doe"
email: "john.doe@example.com"
```

## Core concepts (Phase 1)

### 1. IDL (Interface Definition Language)

`user.proto` is the **contract** between client and server. Both sides generate code from the same file, so they always agree on:

- message field names and types
- RPC method names
- request/response types

You change the API by editing the `.proto`, then recompiling.

### 2. Messages vs service


| In `.proto`                               | Purpose         | Generated Python              |
| ----------------------------------------- | --------------- | ----------------------------- |
| `message User { ... }`                    | Data structure  | `user_pb2.User`               |
| `message UserRequest { ... }`             | Request payload | `user_pb2.UserRequest`        |
| `service UserService { rpc GetUser ... }` | Network API     | Classes in `user_pb2_grpc.py` |


**Field numbers** (e.g. `id = 1`) are permanent on the wire. Never reuse a number for a different field in the same message.

### 3. Why two generated files?


| File               | Generated by        | Contains                                                                      | Responsibility                         |
| ------------------ | ------------------- | ----------------------------------------------------------------------------- | -------------------------------------- |
| `user_pb2.py`      | `--python_out`      | `User`, `UserRequest`                                                         | Serialize/deserialize bytes (protobuf) |
| `user_pb2_grpc.py` | `--grpc_python_out` | `UserServiceStub`, `UserServiceServicer`, `add_UserServiceServicer_to_server` | gRPC networking layer                  |


**Rule of thumb:** `pb2` = *what* travels on the wire; `pb2_grpc` = *how* it is sent and received.

### 4. Key classes you use

#### Client side

- `**grpc.insecure_channel('localhost:50051')`** — TCP connection to the server (no TLS in this POC).
- `**UserServiceStub(channel)`** — Client proxy. Calling `stub.GetUser(...)` performs the RPC.
- `**UserRequest(id=1)**` — The request message object.

#### Server side

- `**UserServiceServicer**` — Base class. Subclass it and override `GetUser`.
- `**add_UserServiceServicer_to_server(servicer, server)**` — Registers your implementation with the gRPC server.
- `**context**` — Per-request object (metadata, deadlines, error codes). Not used heavily in Phase 1.

### 5. Unary RPC

`GetUser` is a **unary-unary** call: one request message in, one response message out.

Other RPC types (not used yet): server streaming, client streaming, bidirectional streaming.

### 6. Server lifecycle

```
create server → register servicer → bind port → start → wait_for_termination
```

In `server.py`:

1. `grpc.server(ThreadPoolExecutor(...))` — handles concurrent RPCs in threads
2. `add_UserServiceServicer_to_server(...)` — wire up your handler
3. `add_insecure_port('[::]:50051')` — listen on all interfaces, port 50051
4. `start()` — begin accepting connections
5. `wait_for_termination()` — block until Ctrl+C

### 7. Insecure vs secure

This POC uses **insecure** channels (no TLS). Fine for local learning; production needs credentials/TLS.

## File-by-file walkthrough

### `protos/user.proto`

```protobuf
syntax = "proto3";

package user;

message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
}

message UserRequest {
  int32 id = 1;
}

service UserService {
  rpc GetUser(UserRequest) returns (User);
}
```

- `syntax = "proto3"` — use proto3 rules (no required fields, etc.)
- `package user` — namespace; shows up in RPC path `/user.UserService/GetUser`
- `service UserService` — becomes the gRPC service name

### `generated/user_pb2.py`

Auto-generated message classes. Use them to build and read data:

```python
from generated.user_pb2 import User, UserRequest

req = UserRequest(id=1)
user = User(id=1, name="Alice", email="alice@example.com")
```

Under the hood: `SerializeToString()` / `FromString()` convert to/from bytes.

### `generated/user_pb2_grpc.py`

Important symbols:


| Symbol                              | Role                                                    |
| ----------------------------------- | ------------------------------------------------------- |
| `UserServiceStub`                   | Client: `stub.GetUser(request)`                         |
| `UserServiceServicer`               | Server base: override `GetUser(self, request, context)` |
| `add_UserServiceServicer_to_server` | Connects servicer to server                             |


RPC path used on the wire: `/user.UserService/GetUser`

### `server.py` (current implementation)

```python
from generated.user_pb2 import User, UserRequest
from generated.user_pb2_grpc import UserServiceServicer, add_UserServiceServicer_to_server

import grpc
from concurrent import futures

class UserService(UserServiceServicer):
    def GetUser(self, request, context):
        print(request)  # debug: see deserialized request on server
        return User(id=request.id, name="John Doe", email="john.doe@example.com")

    def serve(self):
        server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
        add_UserServiceServicer_to_server(self, server)
        server.add_insecure_port('[::]:50051')
        server.start()
        server.wait_for_termination()

if __name__ == "__main__":
    user_service = UserService()
    user_service.serve()
```

**Review notes:**

- Correct: subclasses `UserServiceServicer`, implements `GetUser`, registers servicer, listens on 50051.
- `print(request)` is useful for Step 1.5 — you see `id: 1` when the client calls.
- Returns a hardcoded user for any `request.id` (fine for POC; later you could look up by id).
- Putting `serve()` on the servicer class works but is optional style; a standalone `serve()` function is also common.

### `client.py` (current implementation)

```python
import grpc

from generated.user_pb2 import UserRequest
from generated.user_pb2_grpc import UserServiceStub

def run():
    with grpc.insecure_channel('localhost:50051') as channel:
        stub = UserServiceStub(channel)
        response = stub.GetUser(UserRequest(id=1))
        print(response)

if __name__ == "__main__":
    run()
```

**Review notes:**

- Correct: channel → stub → request → print response.
- Prefer `**localhost:50051`** for the client (connect target). Use `**[::]:50051`** on the server (bind/listen on all interfaces). Using `0.0.0.0` as a client target can behave inconsistently across OSes.

## Request/response lifecycle

```
 client.py                          server.py
     |                                   |
     |  UserRequest(id=1)                |
     |  (Python object)                  |
     v                                   |
 stub.GetUser()                          |
     |                                   |
     |  SerializeToString (protobuf)     |
     |  HTTP/2 over TCP :50051           |
     |---------------------------------->|
     |                                   |  Deserialize → UserRequest
     |                                   |  GetUser(request, context)
     |                                   |  Build User message
     |  HTTP/2 response                  |
     |<----------------------------------|
     |  Deserialize → User               |
     v                                   |
 print(response)                         |
```

Steps in plain language:

1. Client builds `UserRequest(id=1)`.
2. Stub serializes it and sends over gRPC (HTTP/2).
3. Server deserializes into `request`, calls your `GetUser`.
4. Your code returns a `User` protobuf message.
5. Server serializes and sends back; client deserializes and prints.

## Troubleshooting

### `No module named grpc_tools`

```bash
pip install -r requirement.txt
```

Keep `grpcio` and `grpcio-tools` on the **same version** (see `requirement.txt`).

### `No module named generated`

- Run commands from the **project root** (`gRPC/`), not from inside `generated/`.
- Ensure `generated/__init__.py` exists.

### Import error: `import user_pb2` in generated code

After running `protoc`, `user_pb2_grpc.py` may contain:

```python
import user_pb2 as user__pb2
```

Change it to use the package import (see below).

### Import fix after code generation

Replace the top import in `generated/user_pb2_grpc.py`:

```python
# Before (default protoc output)
import user_pb2 as user__pb2

# After (works with our package layout)
from generated.user_pb2 import User, UserRequest
```

Also update references from `user__pb2.UserRequest` → `UserRequest` and `user__pb2.User` → `User` throughout that file.

**Note:** Re-running `protoc` overwrites generated files. Re-apply this fix or add a small post-generate script later.

### `UNIMPLEMENTED` or connection refused

- Start **server before client**.
- Confirm port 50051 is not in use: `ss -tlnp | grep 50051`
- Client target should be `localhost:50051`.

### Version mismatch RuntimeError from `user_pb2_grpc.py`

Upgrade grpcio to match the version used when generating:

```bash
pip install grpcio==1.83.1 grpcio-tools==1.83.1
```

### Step 2.1 — Protobuf serialization (done)

File: `explore_serialization.py`

What it demonstrates:

- `SerializeToString()` → compact binary (what gRPC sends)
- `MessageToJson()` → human-readable JSON (same data, **not** what gRPC sends on the wire)
- `FromString()` and `Parse()` round-trip back to identical `User` objects

Actual output for `User(id=1, name="John Doe", email="john.doe@example.com")`:

```
Raw bytes:  b'\x08\x01\x12\x08John Doe\x1a\x14john.doe@example.com'
Length:     34 bytes

JSON:       70 characters (includes whitespace, field names, punctuation)
```

**Key takeaway:** gRPC carries the **34-byte binary**, not the JSON. JSON is useful for debugging and REST gateways, but the on-the-wire format in this POC is protobuf.

### Step 2.2 — Field tags & wire types (done)

Decode the raw bytes byte-by-byte. Your `User` hex:

```
08 01  12 08 4a6f686e20446f65  1a 14 6a6f686e2e646f652e406578616d706c652e636f6d
```


| Bytes                  | Meaning                                                                  |
| ---------------------- | ------------------------------------------------------------------------ |
| `08`                   | Tag: field **1** (`id`), wire type **0** (varint). Formula: `(1 << 3)    |
| `01`                   | Value: `1` (varint-encoded)                                              |
| `12`                   | Tag: field **2** (`name`), wire type **2** (length-delimited). `(2 << 3) |
| `08`                   | Length: 8 bytes follow                                                   |
| `John Doe`             | UTF-8 string (8 chars)                                                   |
| `1a`                   | Tag: field **3** (`email`), wire type **2**. `(3 << 3)                   |
| `14`                   | Length: 20 bytes follow                                                  |
| `john.doe@example.com` | UTF-8 string (20 chars)                                                  |


**Wire types:**


| Type | Name             | Used for                         |
| ---- | ---------------- | -------------------------------- |
| 0    | Varint           | int32, int64, bool, enum         |
| 2    | Length-delimited | string, bytes, embedded messages |


**Why field numbers matter:** The tag byte is derived from the **field number**, not the name. Renaming `id` → `user_id` in `.proto` does not change the wire format as long as field number stays `1`. Changing field number **breaks** compatibility.

**Exercise for 2.2:** Add to `explore_serialization.py`:

```python
req = user_pb2.UserRequest(id=1)
print("UserRequest hex:", req.SerializeToString().hex())  # expect: 0801
```

Confirmed output:

```
UserRequest hex: 0801
UserRequest length: 2
```

### Step 2.3 — gRPC message framing (done)

File: `explore_framing.py`

Each protobuf payload is wrapped before HTTP/2 sends it:

```
[1 byte: compressed flag] [4 bytes: length, big-endian] [protobuf payload]
```

Create `explore_framing.py`:

```python
import struct
from generated import user_pb2

payload = user_pb2.UserRequest(id=1).SerializeToString()
frame = b'\x00' + struct.pack('>I', len(payload)) + payload
print("Frame hex:", frame.hex())
```

Actual output:

```
Frame hex: 00000000020801
```

Breakdown:

| Bytes | Meaning |
|-------|---------|
| `00` | Compression flag (0 = not compressed) |
| `00000002` | Payload length = 2 (big-endian uint32) |
| `0801` | Protobuf payload (`UserRequest id=1`) |

This 7-byte frame is what HTTP/2 carries as the gRPC message body.

### Step 2.4 — Metadata (done)

Metadata travels **outside** the protobuf message — like HTTP headers.

**Client** sends metadata with the RPC:

```python
metadata = (('client-id', 'my-app'), ('x-api-key', '1234567890'))
stub.GetUser(UserRequest(id=1), metadata=metadata)
```

**Server** reads it via `context.invocation_metadata()`:

```python
for key, value in context.invocation_metadata():
    print(f"{key}: {value}")
```

Use metadata for auth tokens, trace IDs, tenant IDs — things that shouldn't be in every `.proto` message.

### Step 2.5 — Status codes & errors (done)

gRPC errors are **not** Python exceptions on the server. Set status on `context`:

```python
if request.id == 999:
    context.set_code(grpc.StatusCode.NOT_FOUND)
    context.set_details('User not found')
    return User()  # empty body; status carries the error
```

**Client** catches with `grpc.RpcError`:

```python
except grpc.RpcError as e:
    print(e.code(), e.details())  # NOT_FOUND, User not found
```

Verified client output:

```
SUCCESS: id: 1 name: "John Doe" email: "john.doe@example.com"
ERROR: StatusCode.NOT_FOUND User not found
```

### Step 2.6 — Deadlines (done)

**Client** sets a timeout (deadline):

```python
stub.GetUser(UserRequest(id=888), timeout=0.5)  # 500ms max
```

**Server** can check remaining time:

```python
remaining = context.time_remaining()  # seconds, or None if no deadline
```

Server simulates slow work for `id=888` with `time.sleep(2)`. Client timeout of 0.5s triggers:

```
ERROR: StatusCode.DEADLINE_EXCEEDED Deadline Exceeded
```

### Step 2.7 — Observe live traffic (done)

Run server with gRPC tracing:

```bash
GRPC_TRACE=http,call,metadata GRPC_VERBOSITY=DEBUG python server.py
```

Shows HTTP/2 activity, RPC call lifecycle, and metadata on the wire.

## Phase 3 — Streaming RPCs

Phase 1 = **unary** (1 request → 1 response). Phase 3 adds **streams** — multiple messages in one RPC call.

| Step | Topic | RPC pattern | Status |
|------|--------|-------------|--------|
| 3.1 | Server streaming | 1 request → **many** responses | Done |
| 3.2 | Client streaming | **many** requests → 1 response | Done |
| 3.3 | Bidirectional streaming | **many** ↔ **many** | Pending |
| 3.4 | Stream error handling | Cancel / deadline mid-stream | Pending |

### Step 3.1 — Server streaming (done)

**1. Extend `protos/user.proto`:**

```protobuf
message ListUsersRequest {
  int32 page_size = 1;
}

service UserService {
  rpc GetUser(UserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);  // NEW
}
```

**2. Recompile** (and re-apply import fix in `user_pb2_grpc.py`).

**3. Implement on server** — use `yield` instead of `return`:

```python
def ListUsers(self, request, context):
    users = [
        User(id=1, name="Alice", email="alice@example.com"),
        User(id=2, name="Bob", email="bob@example.com"),
        User(id=3, name="Carol", email="carol@example.com"),
    ]
    for user in users[:request.page_size or len(users)]:
        yield user
```

**4. Implement on client** — iterate the response:

```python
for user in stub.ListUsers(ListUsersRequest(page_size=3)):
    print(user)
```

**Key difference from unary:** The server sends multiple frames; the client reads them in a loop until the stream closes.

Generated stub uses `channel.unary_stream` (one request in, stream of responses out).

Current implementation highlights:

- **Server:** `ListUsers` validates `page_size > 0`, then `yield`s each `User` with a 0.5s delay between items (simulates slow DB/page fetch).
- **Client:** `for user in stub.ListUsers(...)` iterates until the stream closes.

Expected output:

```
--- ListUsers streaming ---
received user: id: 1 name: "John Doe" ...
received user: id: 2 name: "Jane Doe" ...
received user: id: 3 name: "Jim Doe" ...
--- ListUsers streaming done ---
```

**Note:** If client `timeout` is shorter than total stream duration (e.g. 0.8s with 3 × 0.5s delays), you get `DEADLINE_EXCEEDED` mid-stream — a preview of Step 3.4.

### Step 3.2 — Client streaming (done)

**Pattern:** Client sends **many** messages; server returns **one** response at the end.

**1. Extend `protos/user.proto`:**

```protobuf
message CreateUsersResponse {
  int32 created_count = 1;
}

service UserService {
  rpc GetUser(UserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);
  rpc CreateUsers(stream User) returns (CreateUsersResponse);  // NEW
}
```

**2. Recompile** and fix imports in `user_pb2_grpc.py`.

**3. Server** — iterate incoming stream with `for`, then return summary:

```python
def CreateUsers(self, request_iterator, context):
    count = 0
    for user in request_iterator:
        print(f"Creating user: {user.name}")
        count += 1
    return CreateUsersResponse(created_count=count)
```

**4. Client** — use a **generator** to send multiple messages:

```python
def user_requests():
    yield User(id=10, name="New User 1", email="u1@example.com")
    yield User(id=11, name="New User 2", email="u2@example.com")

response = stub.CreateUsers(user_requests())
print("Created:", response.created_count)
```

Generated stub uses `channel.stream_unary` (stream in, one response out).

Expected output:

```
--- CreateUsers streaming ---
created count: 3
--- CreateUsers streaming done ---
```

### Step 3.3 — Bidirectional streaming (next)

**Pattern:** Both sides send **many** messages independently.

**1. Add to `user.proto`:**

```protobuf
message ChatMessage {
  string user = 1;
  string text = 2;
}

rpc Chat(stream ChatMessage) returns (stream ChatMessage);
```

**2. Server** — `for message in request_iterator: yield reply`

**3. Client** — generator to send + `for reply in stub.Chat(...)` to receive

Stub type: `channel.stream_stream`.
